# SPEC-501: Man Pages — Implementation Plan

## Approach

The story is ~85% complete. The xtask crate, cargo alias, and five auto-generated section-1 man pages all exist and work correctly. The hand-written `netfyr-examples.7` exists but is incomplete — it is missing three of the ten required scenario sections. The hand-written `man/netfyr-daemon.8` file does not exist at all. Additionally, the xtask log message at line 89 does not mention `netfyr-daemon.8` as a hand-maintained file, and SEE ALSO sections across multiple files should cross-reference `netfyr-daemon(8)`.

The fix is purely additive: create `man/netfyr-daemon.8` as a hand-written troff file, add three missing sections plus a `netfyr-daemon(8)` SEE ALSO entry to `netfyr-examples.7`, update the xtask log message, add `netfyr-daemon(8)` references to SEE ALSO sections in `append_see_also`, and add corresponding unit tests. No new crates, no new dependencies, no changes to the generation pipeline logic.

The `netfyr-daemon.8` file must be hand-written troff (not auto-generated by `clap_mangen`) because the daemon binary has its own `main.rs` in `crates/netfyr-daemon/` with no shared clap definitions with `netfyr-cli`. This is the correct approach — section 8 man pages for system daemons typically contain operational documentation (socket paths, journal behavior, environment variables) that wouldn't be captured in clap argument definitions anyway. The troff conventions established by `netfyr-examples.7` and `netfyr.yaml.5` (hand-maintenance comment on line 1, proper `.TH` header, escaped hyphens with `\-`, `.nf`/`.fi` blocks for examples, `.TP` for tagged paragraphs) will be followed exactly.

## Design Decisions

1. **Decision**: Write `netfyr-daemon.8` as hand-written troff, matching the content in the spec example verbatim.
   - **Alternatives considered**: Adding the daemon binary's clap definitions to `netfyr-cli` and auto-generating. This would require restructuring the daemon crate and wouldn't capture the operational documentation (external change detection, journal, environment variables) that makes the page useful.
   - **Rationale**: The spec explicitly says "The netfyr-daemon(8) page is a hand-written troff file." Section 8 daemon pages are inherently operational, not argument-driven. Following the pattern of `netfyr-examples.7` and `netfyr.yaml.5`.

2. **Decision**: Use the exact section structure from the spec example for `netfyr-daemon.8`: NAME, SYNOPSIS, DESCRIPTION, EXTERNAL CHANGE DETECTION, JOURNAL, ENVIRONMENT, FILES, SEE ALSO.
   - **Alternatives considered**: Adding OPTIONS or EXIT STATUS sections.
   - **Rationale**: The daemon takes no CLI flags (just `netfyr-daemon` with no arguments), and exit codes are not specified. The spec example provides exactly this structure.

3. **Decision**: Add `netfyr-daemon(8)` to SEE ALSO sections in generated pages via `append_see_also`.
   - **Alternatives considered**: Leaving SEE ALSO as-is.
   - **Rationale**: The spec example for `netfyr-apply.1` shows `netfyr-daemon(8)` in SEE ALSO. Cross-referencing the daemon page from subcommand pages helps users discover operational documentation. The top-level `netfyr.1` page should also reference it since it's the daemon that handles submitted policies.

4. **Decision**: Add three missing scenario sections to `netfyr-examples.7` — "Investigating changes with history", "External change detection", and "Reverting to a previous state" — using the content from the spec example.
   - **Alternatives considered**: Leaving them out since the existing tests pass (`nf_count >= 7`).
   - **Rationale**: The acceptance criteria explicitly enumerate all ten sections. The understanding analysis incorrectly claimed these were present; they are not. The spec example provides detailed content for each section.

5. **Decision**: Update `xtask/src/main.rs` line 89 log message to mention `netfyr-daemon.8` alongside `netfyr.yaml.5` and `netfyr-examples.7`.
   - **Alternatives considered**: Leaving it as-is.
   - **Rationale**: Without this, contributors running `cargo xtask man` won't know that `netfyr-daemon.8` is also hand-maintained, and might wonder why it wasn't generated.

6. **Decision**: Use `.TP` (tagged paragraph) for ENVIRONMENT entries in `netfyr-daemon.8`, with environment variable names in `.B` (bold) and defaults in parentheses on the description line.
   - **Alternatives considered**: Using `.IP` (indented paragraph) or plain paragraphs.
   - **Rationale**: `.TP` is the standard troff macro for option/variable lists. `netfyr.yaml.5` and the generated pages already use this convention for their FIELDS and FILES sections.

7. **Decision**: Add the `netfyr-daemon.8` SEE ALSO reference to `netfyr-examples.7` since the spec example includes it.
   - **Alternatives considered**: Not updating examples.7 SEE ALSO.
   - **Rationale**: The spec example for `netfyr-examples.7` shows `netfyr-daemon(8)` in SEE ALSO. The "External change detection" section in examples.7 explicitly says "See netfyr-daemon(8) for full details on limitations," so the cross-reference must resolve.

## File Changes

### 1. `man/netfyr-daemon.8` — CREATE

- **What**: A hand-written troff man page for section 8. Contains:
  - Line 1: `.\"` comment noting the file is maintained by hand, do not edit with cargo xtask man
  - `.TH NETFYR\-DAEMON 8 "" "" "System Manager's Manual"`
  - `.SH NAME`: `netfyr\-daemon \- netfyr network configuration daemon`
  - `.SH SYNOPSIS`: `netfyr\-daemon`
  - `.SH DESCRIPTION`: Overview paragraph covering Varlink socket, DHCPv4 management, external change monitoring, journal recording. Includes systemd startup note with `systemctl start netfyr` example.
  - `.SH "EXTERNAL CHANGE DETECTION"`: Explanatory paragraph followed by four sub-points, each as a `.PP` + `.B` title + description paragraph:
    1. "Only managed interfaces are monitored." — explains policy requirement
    2. "Monitored properties." — lists mtu, state, flags, IPv4 address adds/removals. Notes IPv6, routing, qdiscs are not tracked.
    3. "Debounce window." — 500ms coalescing window
    4. "No automatic re\-reconciliation." — records but does not fight back
  - `.SH JOURNAL`: NDJSON format, stored at /var/lib/netfyr/journal/ by default, includes policy applications/DHCP events/daemon startup/external changes/reverts. Journal rotation at 10,000 entries or 50 MB. Retention at 90 days. References `netfyr history(1)` and `netfyr revert(1)`.
  - `.SH ENVIRONMENT`: Six `.TP` entries:
    - `NETFYR_SOCKET_PATH` (default: /run/netfyr/netfyr.sock)
    - `NETFYR_POLICY_DIR` (default: /var/lib/netfyr/policies/)
    - `NETFYR_JOURNAL_DIR` (default: /var/lib/netfyr/journal/)
    - `NETFYR_JOURNAL_MAX_ENTRIES` (default: 10000)
    - `NETFYR_JOURNAL_MAX_SIZE` (default: 52428800)
    - `NETFYR_JOURNAL_RETENTION_DAYS` (default: 90)
  - `.SH FILES`: Four `.TP` entries for /run/netfyr/netfyr.sock, /var/lib/netfyr/policies/, /var/lib/netfyr/journal/, /etc/netfyr/policies/
  - `.SH "SEE ALSO"`: netfyr(1), netfyr-apply(1), netfyr-query(1), netfyr-history(1), netfyr-revert(1), netfyr.yaml(5), netfyr-examples(7), systemd(1)
- **Why**: This is the only missing man page file. The spec requires it as a hand-written section 8 page documenting daemon behavior. It fulfills acceptance criteria for daemon man page existence, external change detection documentation, journal documentation, and environment variable documentation.

## Risks and Mitigations

1. **Risk**: Troff syntax errors in `netfyr-daemon.8` causing `man` rendering warnings.
   - **Mitigation**: Follow the exact conventions from `netfyr-examples.7` and `netfyr.yaml.5`: escaped hyphens (`\-`), proper `.TH` format, `.TP`/`.PP`/`.RS`/`.RE` nesting. Verify with `man ./man/netfyr-daemon.8` after creation. The existing hand-written pages serve as proven templates.

2. **Risk**: Content in `netfyr-daemon.8` drifting from actual daemon behavior over time (e.g., debounce window changes from 500ms).
   - **Mitigation**: The unit tests check for specific content (e.g., "500" for debounce). If the debounce changes, the tests will continue to pass until someone updates them. This is inherent to hand-written documentation and is noted in the spec. A `read_daemon_man_page()` helper in the tests makes it easy to add content checks later.

3. **Risk**: The `netfyr-examples.7` sections for history/revert reference specific command output formats (table columns, field names) that could change.
   - **Mitigation**: Use the spec example content, which represents the intended output format. The examples are illustrative, not contractual — minor output format changes don't invalidate the examples.

4. **Risk**: `groff` or `man` not available in CI for rendering validation.
   - **Mitigation**: The acceptance criteria for rendering are manual verification steps. The unit tests validate troff content structure (section headers, `.nf` blocks, cross-references) without requiring `groff`. Rendering validation is a manual step.

5. **Risk**: Idempotency test might fail if `generate_man_pages()` touches `netfyr-daemon.8`.
   - **Mitigation**: The `generate_man_pages()` function only writes explicitly named files (netfyr.1, netfyr-{apply,query,history,revert}.1). It has no code path that would write to `netfyr-daemon.8`. The updated idempotency test will verify this.

6. **Risk**: `.TH` line format for section 8 might differ from what `man -s 8` expects.
   - **Mitigation**: Use `.TH NETFYR\-DAEMON 8 "" "" "System Manager's Manual"` which matches the standard format for section 8 pages (e.g., `systemd.service(8)`). The empty third and fourth fields (date and source) are standard practice for project pages without version tracking in the man page header.
