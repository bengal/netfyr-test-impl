# Understand: SPEC-503 — YAML Reference Man Page

## Current State

The project has an existing `man/` directory at the workspace root (`/workspace/project/man/`) containing four files:

| File | Section | How produced |
|------|---------|--------------|
| `man/netfyr.1` | 1 — General commands | Auto-generated by `cargo xtask man` via `clap_mangen` |
| `man/netfyr-apply.1` | 1 — General commands | Auto-generated by `cargo xtask man` |
| `man/netfyr-query.1` | 1 — General commands | Auto-generated by `cargo xtask man` |
| `man/netfyr-examples.7` | 7 — Miscellaneous | Hand-written; has `maintained by hand` comment at top |

**`man/netfyr.yaml.5` does not exist.**

The xtask `man` subcommand (`xtask/src/main.rs`) generates only the section 1 pages from clap definitions. It explicitly skips `netfyr-examples.7` with a printed note. It has no logic touching `netfyr.yaml.5` and will not generate or overwrite it.

The existing section 1 pages already include `netfyr.yaml(5)` in their `.SH "SEE ALSO"` sections (emitted by `append_see_also` in xtask). `netfyr-examples.7` also cross-references `netfyr.yaml(5)` in its SEE ALSO section. These cross-references are forward references to the file this story creates.

The `netfyr-examples.7` page already shows working YAML examples for bare state, multi-document, dhcpv4, and explicit policy formats, confirming the format semantics.

No RPM spec file exists in the repository yet (the `dist/` directory contains only systemd unit files). The RPM integration described in the spec (`%install` / `%files` entries) therefore has no target file to update.

The relevant Rust types that define the documented formats are:
- `netfyr_state::Value` (`enum Value`) — the scalar type mapping
- `netfyr_state::Selector` — selector fields (`name`, `driver`, `mac`, `pci_path`)
- `netfyr_state::schema::FieldType`, `FieldSchemaInfo`, `EntitySchema` — field definitions
- `netfyr_policy::Policy`, `FactoryType`, `parse_policy_yaml` — policy YAML format
- `netfyr_state::yaml::{parse_yaml, parse_state_value}` — bare state parsing
- `netfyr_policy::FactoryType` enum — factory type variants (`static`, `dhcpv4`)

## Requirements

The acceptance criteria translate into the following concrete technical requirements:

1. **File exists**: `man/netfyr.yaml.5` must be present in the repository.
2. **Renders without troff warnings**: The troff source must be syntactically valid.
3. **Standard header**: `.TH NETFYR.YAML 5` header with correct section and title.
4. **NAME section**: Contains `netfyr.yaml — netfyr policy file formats`.
5. **BARE STATE FORMAT section**: Documents the flat format (no `kind` field), explaining that `type`, selector fields, and config fields all appear at the top level. Must include at least one example.
6. **POLICY FORMAT section**: Documents all seven fields: `kind`, `name`, `factory`, `priority`, `selector`, `state`, `states`. Must include examples for both `static` and `dhcpv4` factory types.
7. **MULTI-DOCUMENT FILES section**: Documents `---` separator. Must include at least one example.
8. **SELECTORS section**: Documents all four selector fields: `name`, `driver`, `pci_path`, `mac` (including case-insensitivity note for `mac`). Notes the special dhcpv4 wrapping.
9. **FIELDS section**: Documents the ethernet fields: `mtu`, `addresses`, `routes`, `state`. Each field needs type, optionality, and description.
10. **VALUE TYPES section**: Table mapping YAML scalar types to netfyr types (`Bool`, `U64`, `I64`, `IpAddr`, `IpNetwork`, `String`, `List`, `Map`).
11. **FILES section**: Lists `/etc/netfyr/policies/` and `/var/lib/netfyr/policies/`.
12. **SEE ALSO section**: References `netfyr(1)`, `netfyr-apply(1)`, `netfyr-query(1)`, `netfyr-examples(7)`.
13. **Hand-written marker**: Comment at top noting the file is maintained by hand (consistent with `netfyr-examples.7` convention).
14. **`man ./man/netfyr.yaml.5` renders**: The file must be viewable with `man` directly.

## Integration Points

- **`man/netfyr-examples.7`**: Already cross-references `netfyr.yaml(5)`. The new file must exist for this reference to resolve. The examples page covers "how to use" scenarios; the new page covers the reference definition of every field and format.
- **`man/netfyr.1`, `man/netfyr-apply.1`, `man/netfyr-query.1`**: All emit `netfyr.yaml(5)` in their SEE ALSO via `append_see_also` in xtask. The new file fulfills these existing forward references.
- **`xtask/src/main.rs`**: Must remain untouched. The printed note already says `netfyr-examples.7` is not modified; the same convention applies to `netfyr.yaml.5` — the xtask has no logic for it and needs none.
- **RPM spec (SPEC-502)**: No spec file exists in the repo yet. When it is added, it will need the `%install` and `%files` entries shown in the story spec. This is out of scope for the current story but the new man page file must be in place for that future integration.

## Risks

1. **Troff syntax errors silently degrade rendering**: `man` renders invalid troff with missing sections or garbled text rather than failing. Verification requires actually running `man ./man/netfyr.yaml.5` and checking for `troff` warnings, not just file existence.

2. **`netfyr-examples.7` forward reference already exists**: The examples page refers to `netfyr.yaml(5)`. If the new file's title macro or NAME entry doesn't match exactly what `man` expects for section 5 lookup, cross-references from other pages may not resolve. The `.TH` line must be exactly `.TH NETFYR.YAML 5` (or equivalent case).

3. **`routes` field documentation completeness**: The spec documents `routes` as a sequence of mappings with `destination`, `gateway`, and optional `metric`. The Rust code supports this but the schema details (required vs optional fields within a route entry) are defined in the schema JSON files under `crates/netfyr-state/src/schemas/` which were not surfaced in the context snapshot. The man page content in the spec is sufficient to follow, but if the schema diverges, the man page may be inaccurate.

4. **`state` field name collision**: The ethernet `state` configuration field (values: "up"/"down") has the same name as the `state` key in the policy format (`state:` mapping). The man page must be unambiguous about which context each `state` refers to.

5. **No automated rendering test in CI**: The acceptance criteria require running `man ./man/netfyr.yaml.5` and observing no troff warnings. There is no existing CI infrastructure for man page validation in the repository (no Makefile, no test scripts visible). Verification is a manual step.

6. **Scope boundary with SPEC-502 (RPM)**: The story states the RPM spec installs this file, but no RPM spec exists yet. This story only creates the troff source; RPM integration is deferred to SPEC-502.
